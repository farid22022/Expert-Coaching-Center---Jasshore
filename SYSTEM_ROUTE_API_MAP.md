## Key state transitions

1. Admin-owned `Course` is published with its persisted `admission_form_schema`.
2. Applicant creates an `AdmissionApplication`. Admin approves/rejects on the backend.
3. If the admission fee is positive, payment service checks approval, creates/uses a bKash agreement, and initiates a transaction. Only backend verification can mark `AdmissionPaymentTransaction` completed and activate an `Enrollment`; the service retries activation idempotently if needed.
4. Head Teacher owns assigned-course stages/sections/subjects/weekly schedule and teacher assignment. Subject Teacher authors only assigned-subject material, questions and assessments. Teacher-authored publishable content needs Head Teacher review.
5. The student content API checks active enrollment, publication/review status, `publish_at` and `SubjectWeek.release_at` before returning a lesson or assessment. The signed file endpoint checks those gates again for each media request, including video byte-range requests.
6. Student attempts and assignment submissions are scoped to their own student record. Grading updates the existing submission, creates a notification, and published course results are the only results exposed to students.

## Ownership and storage notes

`Course` is the admission/program record; `CourseMaterial` is also the lesson/video/PDF record linked to `CourseChapter`. No second Admission or Lesson model was introduced. Actual lesson uploads use the Django `FileField` media storage. URLs from the student content endpoints are signed, expire after one hour, and are rechecked against enrollment and publication when fetched. Deployment must keep raw `MEDIA_ROOT/assessments/materials/` files inaccessible at the web-server/CDN layer; the Django signed endpoint is the intended student delivery path.
